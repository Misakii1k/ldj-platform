# 共用游戏引擎渐进式重构设计

## 目标

在保留现有 `GameModule` 契约、服务端权威执行链和模块化单体结构的基础上，通过渐进式提取单一职责规则原语、统一视角契约、统一桌面 UI 和标准化开发工具链，降低后续游戏接入成本。

设计同时满足以下目标：

- 不因过早抽象导致引擎僵化。
- UNO 与《谁是卧底》迁移前先建立完整局安全网。
- 游戏模块通过组合原语表达差异化规则，不在共用层增加具体游戏分支。
- 新游戏无需重复实现房间、事务、恢复、广播、计时器、机器人驱动和通用桌面结构。
- 新游戏模块代码量相较旧接入方式减少至少 40%。
- 所有正式上架游戏共用统一桌面 UI、视觉语言和触控标准。
- 媒体能力单独排期，不阻塞纯状态游戏引擎。

## 规范优先级与产品合规边界

本设计是游戏准入、规则来源和共用引擎迁移的最高优先级规范。与本设计冲突的既有实施计划，在完成修订前不得继续执行；尤其不得依据旧计划将资料不完整的候选游戏通过原创补全标记为可上架。

### 授权复刻轨道

除明确禁入的游戏外，候选游戏只能在取得合法数字改编授权和可靠官方规则来源后进入授权复刻轨道。

“原版 1:1 复刻”在本设计中仅指锁定规则集的规则语义等价，不表示未经授权复制像素级 UI、规则书文字、美术、音效或商业标识。每个授权复刻规则集必须锁定：

- 出版方或权利方。
- 产品名称、地区、语言、版本或 SKU。
- 规则书版本和发布日期。
- 包含及排除的扩展。
- 经批准的数字化适配项。
- 授权记录编号、权利范围和到期日。
- 权利审批人与规则审批人。

名称、核心流程、角色结构、牌组构成、胜负条件和计分规则以该锁定版本为准。规则来源冲突时，以授权方书面确认、锁定版本规则书、官方勘误和官方补充说明的顺序裁决。

任何家庭规则、平台规则或原创裁定必须使用独立 `rulesetId`，明确标记为平台变体，不得使用“官方”“标准”或授权原版规则集名称。规则缺失或授权证据不完整时，模块只能处于 `internal_prototype` 或 `blocked_rights`，不得标记为 `playable`。

每条可发布规则必须建立“来源条款 → 状态转换 → 自动测试”的映射。官方规则后续更新不会自动改变进行中或已发布规则集，必须创建新规则集版本并重新审批。

### 《骗子酒馆》永久禁入矩阵

《骗子酒馆》永久排除，禁止通过更名或“原创版”规避：

- 生产客户端：禁止名称、别名、游戏 ID、角色、规则文案、图像、音频和规则实现。
- 生产服务端：禁止模块、注册项、配置、种子数据、测试夹具和运行时分支。
- 发布包：禁止相关资料、目录、源文件、静态资源和生成物。
- 游戏目录与搜索索引：禁止候选卡片、`coming_soon` 条目、标签和推荐信息。
- 共用引擎测试：禁止将其特有规则作为原语测试样本。
- 内部研究资料：允许保留在不参与构建、打包、产品索引和代码生成的隔离资料区，但不得被运行时代码引用。

禁入扫描至少覆盖“骗子酒馆”“Liar's Bar”“liars-bar”“liars_bar”及对应模块、路由和资源标识。构建和发布前必须扫描客户端产物、服务端产物、registry、catalog、路由和静态资源；任一命中均阻止发布。

## 风险与原则

### 主要风险

过早设计完整通用引擎会迫使共用层根据少数游戏增加条件分支，最终形成难以扩展的配置式巨型状态机。

### 控制原则

- 每个原语只解决一个问题。
- 通过组合扩展，不通过游戏 ID 条件分支扩展。
- 先在真实游戏中重复使用，再稳定 API。
- 先补测试，再迁移规则。
- 接入容易不等于准入宽松。
- 共用引擎必须先通过 UNO 和《谁是卧底》的完整局回归，再允许新游戏依赖稳定原语。

## 方案选择

采用渐进式原语提取方案。

不采用以下方案：

- 先设计完整通用引擎：迁移面过大，容易过拟合两款游戏。
- 声明式规则 DSL：UNO 的罚牌链、竞速窗口和终局特殊结算，以及《谁是卧底》的异步裁判追溯，会导致 DSL 膨胀并产生大量逃生钩子。

保留现有执行平台和 `GameModule` 契约，只提取已经在真实游戏中重复出现且边界稳定的纯函数能力。

## 架构边界

### 共用执行平台负责

- 房间与对局生命周期。
- 每房间串行事务。
- 动作信封校验、身份认证和幂等。
- 调用游戏模块的纯函数状态转换。
- 事件、效果、快照和结果的原子持久化。
- 定向玩家视角与观战视角广播。
- 确定性随机源。
- 计时器调度、取消和过期保护。
- 断线重连与崩溃恢复。
- 机器人动作驱动。
- 外部裁判任务的生命周期、幂等和失败回退。

### 游戏模块负责

- 配置和动作 Schema。
- 初始状态。
- 合法动作集合。
- 游戏阶段和当前行动者。
- 规则状态转换。
- 私有信息向玩家、队友、淘汰者和观战者视角的映射。
- 胜负、排名和计分。
- 机器人合法候选和策略提示。
- 快照版本迁移。
- 官方规则条款与实现测试映射。

### 共用原语负责

原语是无状态、不可变、单一职责的纯函数工具。原语不得：

- 读写数据库。
- 广播 WebSocket。
- 调用大模型。
- 识别具体游戏 ID。
- 决定某款游戏的胜负。
- 同时处理流程推进、投票和结算等多个问题。

依赖方向为：

```text
服务端执行平台
    ↓ 调用
GameModule 契约
    ↓ 组合
单一职责规则原语
```

## 原语目录

### `setup`

负责座位建立、队伍或阵营分配所需的通用操作、确定性顺序随机化、配置标准化和初始资源分发。

不负责具体角色比例、具体牌组定义和胜负条件。

### `turns`

负责：

- 顺时针和逆时针轮转。
- 跳过指定数量玩家。
- 排除淘汰、退出或不可行动玩家。
- 固定顺序、随机起点和轮换起点。

由游戏模块决定何时反转、跳过或应用双人特例。

### `cards`

负责：

- 牌实例唯一标识。
- 牌组生成。
- 确定性洗牌。
- 摸牌、发牌和区域移动。
- 手牌、摸牌堆和弃牌堆等区域。
- 保留顶牌后回收弃牌。
- 动态加入完整新牌组。

不负责具体牌的合法性、罚牌链和牌面分值。

### `ballot`

负责：

- 投票资格和候选资格。
- 禁止自投等通用约束。
- 锁票和幂等。
- 缺席票。
- 计票、最高票集合和平票集合。

不负责加赛、淘汰、身份公开和胜负判断。

### `visibility`

负责通过白名单生成：

- 公共字段。
- 玩家私有字段。
- 队伍字段。
- 淘汰者字段。
- 观战者字段。
- 终局公开字段。

不得先复制完整权威状态再删除秘密字段。

### `timing`

负责：

- 计时器令牌。
- 轮次、阶段和序号绑定。
- 过期判断。
- 竞速窗口。
- 多个结算动作中先提交事务者生效。

窗口只描述参与者、允许动作、关闭条件和截止时间，不决定处罚。

### `flow`

负责当前阶段验证、合法 actor 验证、阶段序号、进入记录、完成条件组合和状态迁移断言。

不提供自动流程 DSL，游戏模块继续显式编写阶段转换。

### `scoring`

负责：

- 分值聚合。
- 小局分数记录。
- 整场累计。
- 升序或降序排名。
- 并列名次。
- 个人与队伍聚合。
- 固定小局数结束条件。

不定义具体牌面值或阵营胜负。

### `adjudication-policy`

这是纯函数原语，负责输入标准化、本地精确匹配、外部裁判结果分类、回退决策和迟到结果资格判断。它不得发起网络请求、持久化任务、调度重试或恢复任务。具体裁判输入、判定标准和胜负后果由游戏模块定义。

### `adjudication-runner`

这是共用执行平台中的有状态服务，不属于规则原语，负责创建并持久化外部任务、调用主模型和备用模型、处理超时与恢复，并将结果转换为系统动作回灌串行事务链。它只执行游戏模块与裁判策略，不直接决定游戏胜负。

## 原语成熟度

### 实验原语

- 仅一款游戏使用。
- API 允许调整。
- 具备单元测试、不可变性测试和确定性测试。
- 其他正式游戏不得依赖。

### 候选原语

- 至少两款结构不同的游戏真实使用。
- 两款游戏均通过完整局回归。
- 不包含具体游戏 ID 分支。
- 输入输出类型稳定。
- 覆盖空集合、重复动作、非法 actor 和恢复边界。

### 稳定原语

- UNO 与《谁是卧底》相关回归全部通过。
- 至少一款第三方验证游戏真实复用。
- 通过确定性重放、快照恢复、不可变性和视角泄漏验证。
- 机器人和真人动作共用相同合法性入口。
- 破坏性修改必须升级版本或提供迁移层。

第三款验证游戏允许在独立功能分支或 feature flag 下依赖候选原语，但在原语晋升稳定前不得标记为 `playable`。候选 API 变更必须同时回归 UNO、《谁是卧底》和第三款验证游戏；验证失败时允许修改或撤销候选 API。

## 标准游戏模块骨架

```text
games/<game-id>/
├─ shared/
│  ├─ manifest
│  ├─ config
│  ├─ actions
│  └─ views
├─ server/
│  ├─ state
│  ├─ module
│  ├─ rules
│  ├─ scoring
│  └─ bot
├─ client/
│  ├─ table
│  ├─ controls
│  └─ result
└─ tests/
   ├─ rules
   ├─ invariants
   ├─ replay
   ├─ full-game
   └─ views
```

模板只建立契约位置，不生成伪业务逻辑。

新增游戏必须明确：

1. 初始状态。
2. 每个动作的合法条件。
3. 动作对应的新状态。
4. 各类参与者的可见信息。
5. 小局和整场结束条件。
6. 计分方式。
7. 机器人合法候选。
8. 官方规则条款对应测试。

## 能力声明

游戏通过 manifest 声明桌面和测试所需能力，例如：

```text
usesCards
usesVoting
usesTeams
usesPrivateRoles
usesRoundScoring
usesBuzzer
usesTextInput
usesAsyncAdjudication
```

能力声明只用于加载通用桌面区域、启用契约测试、校验必要接口和生成规则检查清单。

能力声明不得触发服务端规则结论。例如 `usesVoting` 不能自动表示最高票者被淘汰。

## 统一动作信封

客户端、机器人、计时器和外部裁判结果使用同一种动作信封：

```text
requestId
sessionId
actor
expectedSequence
actionType
payload
clientTimestamp
```

- `requestId` 保证网络重试幂等。
- `actor` 可以是玩家、机器人、系统计时器或裁判服务。
- `expectedSequence` 防止旧状态动作在新状态中被重新解释。
- `actionType` 和 `payload` 由游戏模块严格解析。
- `clientTimestamp` 只用于诊断，不参与权威排序。

权威顺序以服务端事务提交顺序为准。

## 动作数据流

```text
动作进入
→ 房间串行队列
→ 会话状态检查
→ requestId 幂等检查
→ expectedSequence 检查
→ GameModule.parseAction
→ GameModule.reduce
→ 不变量检查
→ 写入游戏事件
→ 写入 effect
→ 更新随机状态
→ 写入快照
→ 判断小局或整场结果
→ 提交事务
→ 生成每位订阅者视角
→ 定向广播
→ 调度计时器、机器人或外部任务
```

原则：

- 合法性判断发生在事务提交前。
- 被拒绝动作不推进事件序号。
- effect 只描述副作用，不在纯函数中执行。
- 广播发生在事务提交后。
- 机器人、计时器和外部裁判不能直接修改状态。

## `reduce` 输出

迁移后的版本化 `GameModule` 契约必须返回：

```text
nextState
publicEvents
privateEvents
effects
resultCandidate
diagnostics
```

- `nextState` 是完整的新状态，不允许原地修改旧状态。
- `publicEvents` 只包含所有玩家可知的规则事实。
- `privateEvents` 必须声明明确接收者集合。
- `effects` 描述计时器、机器人、外部裁判和系统消息等副作用。
- `resultCandidate` 可以提出小局或整场结果，但平台负责正式落库。
- `diagnostics` 只在开发和测试环境启用，不得进入普通客户端视角。

## 竞速窗口

统一窗口结构：

```text
windowId
kind
openedAtSequence
eligibleActors
allowedActions
closesAt
closeOnActionTypes
resolution
```

窗口只定义谁可以操作、允许动作、关闭条件、截止时间和是否已结算。处罚和流程后果仍由游戏模块决定。

同一会话允许并行窗口。每个窗口只能结算一次，所有竞争动作按服务端事务顺序裁决。

## 异步裁判

白板猜词等异步裁判使用以下流程：

```text
提交猜词
→ 本地精确匹配
├─ 成功：立即回灌裁判结果动作
└─ 失败：创建外部任务
          → 主模型
          → 备用模型
          → 回灌裁判结果动作
```

提交时冻结资格和标准答案版本。后台裁判期间普通流程可以继续；如果普通流程产生终局，只记录暂存结果。更早提交的猜词成功时覆盖暂存结果，猜错时确认暂存结果或继续当前对局。

事件记录裁判结论，重放时不再次调用模型。

## 视角生成

权威状态提交后，平台按订阅者身份调用游戏模块生成视角：

```text
toPlayerView(state, playerId)
toSpectatorView(state)
```

视角必须从白名单重新构建。标准视角元数据包括：

```text
phaseLabel
currentActor
seatStatus
countdown
availableCapabilities
publicLog
resultSummary
```

游戏专属数据放在带版本的扩展字段。统一桌面只消费标准字段，专属组件只消费扩展字段。

## 异常处理

### 用户输入错误

非法 actor、非法牌、无效候选人、重复投票、过期窗口动作和旧序号动作均被拒绝：

- 不写游戏事件。
- 不推进序号。
- 返回稳定错误代码。
- 客户端使用最新视角重渲染。

系统不得把非法动作自动改写为另一个动作。

### 幂等重试

相同 `requestId` 必须返回首次结果，不重复摸牌、投票、计分、调度计时器或创建外部任务。

### 规则模块内部错误

`reduce` 异常、状态 Schema 失败、不变量失败、未知 effect 或不可序列化数据会导致事务回滚。会话进入 `SUSPENDED`，平台尝试从最近有效快照和事件恢复。无法确定性恢复时明确异常终止，不猜测修补权威状态。

### 持久化和广播失败

数据库事务失败时：

- 不广播成功。
- 不执行 effect。
- 允许客户端用相同 `requestId` 重试。

事务已提交但广播失败时，权威状态保持成功，客户端通过重连或序号补偿恢复，不回滚已提交动作。

## 不变量

### 平台不变量

- 事件序号严格递增。
- 同一 `requestId` 只对应一个结果。
- 快照版本可识别。
- 已结束对局不接受普通动作。
- 活跃计时器绑定有效会话和阶段序号。
- 正式结果只写入一次。

### 通用规则不变量

- 玩家、座位和队伍引用有效。
- 当前行动者属于可行动集合。
- 同一牌实例只存在于一个区域。
- 投票者最多拥有一张锁定票。
- 私有事件具有明确接收者。
- 已关闭窗口不能再次结算。
- 一次性能力不能重复消耗。

### 游戏专属不变量

游戏模块注册自身约束。

UNO 至少包括：

- 所有牌实例 ID 唯一。
- 当前顶牌存在。
- 有效颜色始终可判定。
- 罚牌链类型与响应集合一致。
- 小局结束时恰有一个出完牌者。
- 累计分等于各小局分之和。

《谁是卧底》至少包括：

- 白板模式恰有一名白板且没有有词卧底。
- 普通模式不存在白板。
- 存活玩家可在发言和投票资格结构中解释。
- 白板猜词机会最多一次。
- 已提交异步裁判的资格快照不可改变。
- 身份公开配置与所有视角一致。

## 断线与重连

断线只改变连接状态，不立即改变游戏身份或规则状态。

保留期内：

- 座位、手牌、身份和投票资格保留。
- 计时器继续运行。
- 断线玩家按游戏既定超时规则处理。
- 重连后从最新权威视角继续。

重连握手包含：

```text
sessionId
playerId
lastSeenSequence
connectionToken
```

事件差距较小时返回缺失公开事件和最新视角；差距过大或视角版本变化时返回完整最新视角。服务端不得发送完整权威状态或其他玩家私有事件。

保留期结束后，平台提交 `player_retention_expired` 系统动作。退出、机器人接管、缺席、提前胜负或异常终止由游戏模块决定。

## 崩溃恢复

恢复流程：

```text
读取最新有效快照
→ 校验摘要和版本
→ 加载快照后的事件
→ 确定性重放
→ 运行完整不变量
→ 恢复未完成 effect
→ 重建计时器和外部任务
→ 重新开放会话
```

### 计时器恢复

- 截止时间未到时按剩余时间重新调度。
- 截止时间已过时投递一次超时系统动作。
- 相同令牌已经结算时不重复执行。
- 阶段序号不匹配时作为过期计时器无操作结束。

### 机器人恢复

机器人只通过普通动作信封提交动作。未提交动作在恢复后根据当前合法候选重新选择；已提交动作依靠 `requestId` 幂等。模型自由输出不得绕过合法候选集合。

### 随机状态恢复

随机源内部状态进入快照。事件重放使用已记录随机结果，恢复后的新动作从快照随机状态继续，不因重启重新洗牌、选角色或选先手。

## 快照版本与规则版本

每个快照携带：

```text
gameId
rulesetId
schemaVersion
engineContractVersion
createdAtSequence
stateDigest
```

迁移规则：

- 只允许显式单向迁移。
- 每个迁移函数只处理相邻版本。
- 迁移函数必须是纯函数。
- 迁移后运行状态 Schema 和完整不变量。
- 不允许读取时静默补默认字段掩盖结构变化。
- 无法迁移时暂停或异常终止，不猜测状态。

`schemaVersion` 表示存储结构，`rulesetId` 表示规则本身。改变胜负条件、牌组构成或身份规则必须新建规则集版本，旧对局继续使用开局时锁定的版本。

## 外部模型失败策略

白板猜词裁判链为：

```text
本地精确匹配
→ 主模型
→ 备用模型
→ 仍失败则猜错
```

调用约束：

- 只发送标准词和玩家答案。
- 不发送整局聊天、房间信息或其他秘密。
- 使用结构化输出和明确超时。
- 主模型与备用模型独立判断。
- 备用模型不能看到主模型结论。
- 不记录 API 密钥和完整供应商请求头。

结果类别为 `equivalent`、`not_equivalent`、`uncertain`、`provider_error`、`timeout` 和 `invalid_response`。只有 `equivalent` 判定正确；非明确结果触发备用模型；备用模型仍无明确结果时判定猜错。

外部任务具有唯一 `taskId`。迟到结果在任务已结算后丢弃；服务器重启后继续未完成任务，不重新消耗猜词机会；事件重放不再次调用模型。

## 无法恢复的结果类型

```text
COMPLETED
ABORTED_ALL_LEFT
ABORTED_BY_HOST
FAILED_RECOVERY
FAILED_INVARIANT
FAILED_RULESET_UNAVAILABLE
```

异常终止不得伪造获胜者、计入正常胜场、泄露完整权威状态或静默覆盖原对局。

## 已确认的 UNO 平台规则集

以下规则属于独立平台变体 `uno_platform_house_v1`，不是授权官方规则集，不得称为“标准规则”或原版 1:1 复刻。

本规则集不存在隐式推荐规则。下列条款与已明确采用的后续默认条款共同构成锁定规则；未列明、未测试或未映射来源的边界一律视为未决定，并阻止该规则集上架。新增或修改规则必须升级 `rulesetId`，或作为开局前锁定并写入快照的显式配置变体。

当前磁盘实现是 `uno_legacy_platform_v1` 兼容基线。迁移前必须建立差异表，每项标记 `KEEP_COMPAT`、`CHANGE_RULESET` 或 `REMOVE_PLAYABLE`。黄金回放只证明兼容性，不证明新平台规则正确性。新规则集通过全部准入测试前，不得替换 legacy 规则集或以“标准规则”展示。

### 基础回合

- 摸牌后可以打出手中任意合法牌。
- 普通回合 15 秒超时后温和托管。
- 有合法牌时，托管按保守优先级从合法候选中选择。
- 无合法牌时自动摸一张，摸后不继续出牌。
- 托管导致剩一张时系统原子化自动喊 UNO。
- 双人个人模式中，反转牌等同跳过。

### UNO 声明

- 玩家恰有两张牌且已选择合法牌时，才允许提前喊 UNO。
- 提前喊只在当前回合有效，不可主动取消。
- 提前喊后可在合法牌之间切换，不合法牌可见但不可点按。
- 未提前喊时，手牌变为一张后开启 5 秒竞速窗口。
- 玩家可补喊，其他玩家可点按其泛光并带小喇叭提示的头像抓漏报。
- 补喊与抓漏报按服务端事务顺序竞速。
- 抓漏报成功时目标摸两张；错误抓漏报不处罚。
- 下一位玩家可并行开始回合；其有效出牌或摸牌会提前关闭竞速窗口。
- 5 秒内无人操作则窗口自然关闭且不处罚。

### 罚牌链与质疑

- `+2` 后可以接 `+2` 或 `+4`。
- `+2` 链接入 `+4` 后升级为 `+4` 链。
- `+4` 后只能接 `+4`，不能接 `+2`。
- 普通状态直接打出的第一张 `+4` 可以被下家质疑。
- 第二张 `+4` 叠加后整条链关闭质疑。
- 用 `+4` 响应 `+2` 链时不允许质疑。
- 无法或不愿继续叠加者摸取全部累计罚牌并跳过。
- 罚牌摸牌不进入摸后可出牌阶段。
- 质疑成功时出 `+4` 者摸四张，所选颜色作废，质疑者正常行动。
- 质疑失败时质疑者摸六张并跳过。
- `+4` 响应窗口和 `+2` 罚牌响应窗口均采用 5 秒；超时自动接受罚牌。

### 终局、计分与多小局

- 最后一张为 `+2` 时禁止叠加，下家固定摸两张后结算。
- 最后一张为 `+4` 时禁止质疑和叠加，下家固定摸四张后结算。
- 罚牌计入下家最终手牌分。
- 数字牌按数字计分，功能牌 20 分，变色牌和 `+4` 为 50 分。
- 个人模式按剩余手牌总分从低到高排名，同分共享竞赛名次。
- 双人组队模式固定四人，队友交错入座，队友手牌完全隐藏，对局内禁止策略交流。
- 任意队员出完牌后小局结束，两名队员分数相加，低分队获胜；同分判平局。
- 房主选择 1、3、5 或 7 小局，整场按累计低分排名。
- 首局随机先手，后续由上一小局出完牌的玩家先手。
- 个人模式支持 2 至 10 人。

### 牌堆

- 开局允许任意牌作为首张弃牌，但不触发其功能效果。
- 首张为变色牌或 `+4` 时由确定性随机源选择初始颜色。
- 摸牌堆耗尽时保留弃牌顶牌，将其余弃牌重新洗回。
- 可用牌不足以完成摸牌或罚牌时，动态加入完整 108 张新牌，并与原可用牌一起洗牌。
- 一小局可按需多次扩牌。
- 新小局重置为一副标准 108 张牌。

## 已确认的《谁是卧底》规则集

《谁是卧底》拆分为两个独立规则集：

- `undercover_classic_v1`：仅平民与有词卧底，作为现有实现的迁移兼容基线。
- `undercover_blank_v1`：包含白板、猜词和异步裁判，在独立验收完成前不得标记为 `playable`。

两个规则集不得用可变配置改变角色语义。身份公开方式和双卧底互认等开局配置必须写入快照并在对局中锁定。

### 经典规则集

- 淘汰玩家进入完全旁观状态，不再发言、投票或发送自由文本。
- 发言超时自动跳过，不由机器人或大模型代发。
- 房主可配置淘汰身份即时公开或终局统一公开。
- 8 至 12 人双卧底局可由房主配置卧底互认或不互认。
- 首轮随机发言起点，后续每轮轮换起点。
- 平票加赛由所有存活玩家投票。
- 加赛前平票候选人依次获得一次限时辩解。
- 1 名卧底局在剩余两人且卧底存活时卧底获胜。
- 2 名卧底局在剩余三人且至少一名卧底存活时卧底获胜；若该语义与授权原版不一致，必须使用独立平台变体 `rulesetId`，不得覆盖授权经典规则集。

### 白板规则集

- 房主可选择启用白板模式，支持 4 至 12 人，提示 5 至 8 人体验更平衡。
- 白板始终只有一名。
- 启用白板后没有其他有词卧底，其余玩家都是持有同一平民词的平民。
- 白板视为卧底方，无词。
- 场上只剩白板与一名平民时，白板立即获胜。
- 白板整局只有一次猜平民词机会。
- 存活期间除结算外可以随时秘密提交猜词。
- 主动猜中立即获胜；猜错立即淘汰且不再获得第二次机会。
- 白板从未主动猜词而被投票淘汰时，立即获得最终猜词机会。
- 即时公开身份模式下，先公开白板身份，再进行最终猜词。
- 猜词先标准化并精确匹配；失败后依次使用主模型和备用模型做同概念裁判。
- 两个模型均失败或不确定时判定猜错。
- 后台裁判不中断普通流程。
- 猜词结果按提交时间追溯；提交时有效的猜词成功可覆盖其后产生的暂存普通结果。

游戏不得重复实现房间顶栏、网络状态、座位框架、计时器、系统消息和通用结算层。

客户端按能力启用控件，服务端再次执行权威校验。能力只描述当前能做什么，不暴露完整规则状态。

## 迁移顺序

迁移分为四个独立批准门：

- D1 规则与合规基线：冻结 ruleset、授权证据、禁入矩阵和目录状态，不修改引擎。
- D2 低风险规则原语：只提取确定性随机、座位轮转、牌区基础操作和可见性工具，不引入外部模型或统一全部 UI。
- D3 迁移与兼容：迁移 `uno_legacy_platform_v1` 和 `undercover_classic_v1`，完成黄金回放、快照和视角兼容。
- D4 新增能力：独立交付 UNO 新平台规则、白板与异步裁判、统一桌面和第三游戏验证；每项具有独立上线门。

未经 D1 批准，不得稳定原语 API；未经 D3 批准，不得用新规则替换兼容基线。

### 阶段 0：冻结基线

- 创建独立开发分支。
- 记录当前类型检查、代码检查、测试和构建结果。
- 固定 UNO 与《谁是卧底》的关键随机种子。
- 保存玩家视角快照和完整局黄金回放。
- 修正文档与目录中的状态漂移。

### 阶段 1：补测试，不迁移规则

补齐：

- UNO 完整单局、罚牌链、质疑、喊 UNO、排名、组队、动态扩牌。
- UNO 崩溃恢复和机器人完整收束。
- 《谁是卧底》白板模式和异步裁判追溯。
- 两款游戏的不可变性和视角泄漏测试。

### 阶段 2：提取低风险原语

依次提取确定性随机、座位轮转、计时器令牌、可见性白名单、唯一实例 ID、排名和并列。

每个原语先在一款游戏替换并回归，再在第二款游戏使用并跑全量回归，达标后晋升候选。

### 阶段 3：提取中风险原语

提取牌区移动与回收、投票资格与计票、通用竞速窗口、多小局累计和外部裁判任务生命周期。

### 阶段 4：统一视角和桌面 UI

先统一视角标准字段，再迁移阶段、行动者、倒计时、座位、事件、动作容器和结算框架，最后接入游戏专属主舞台。

### 阶段 5：模块脚手架和契约测试

两款迁移游戏稳定后，提供生成器、契约测试、视角快照、完整局驱动、规则映射和诊断工具。

### 阶段 6：第三款游戏验证

第三款游戏用于验证：

- 不修改执行平台。
- 不增加游戏 ID 分支。
- 房间、事务、恢复、广播、计时器、机器人驱动和桌面骨架共 7 项基础设施中，至少 6 项直接复用且不复制实现。
- 游戏模块非测试 TypeScript 有效代码行相较同功能清单下的旧 `GameModule` 对照实现减少至少 40%；排除生成文件、空行、纯类型声明和静态题库，由固定脚本比较基线提交与目标提交。
- 能通过模板和契约测试完成纯规则闭环。

任何允许游戏绕过原语不变量、直接修改原语内部状态或注入游戏 ID 分支的接口都算逃生钩子。候选原语晋升稳定时允许的逃生钩子数量为 0。

## 测试策略

### 原语单元测试

覆盖正常输入、空集合、边界数量、重复动作、非法 actor、不可变性、确定性、输入顺序变化和失败时不修改原状态。

### 游戏规则测试

每条规则至少映射一个测试：

```text
规则来源
→ 规则条款编号
→ 状态前置
→ 玩家动作
→ 预期状态
→ 预期视角
→ 预期事件
```

### 契约测试

所有游戏自动验证：

- 配置和动作严格解析。
- 初始状态可序列化。
- `reduce` 不修改输入。
- 相同种子和动作序列产生相同结果。
- 被拒绝动作不推进状态。
- 所有视角满足 Schema。
- 玩家和观战视角无秘密泄漏。
- 正式结果只产生一次。
- 快照可保存、读取和重放。
- 机器人动作始终来自合法候选。

### 完整局模拟

完整局定义为从 `createInitialState` 开始，到产生唯一正式结果结束。每个场景必须配置最大动作数和最大虚拟时间，超过上限即失败。

每款游戏覆盖：

- 最短结束路径和场景上限内的最长边界路径。
- 每种胜利、平局和并列条件。
- 全真人、全机器人和混合动作驱动。
- 中途断线与恢复。
- 服务器崩溃与恢复。
- 幂等重试。
- 固定随机种子的确定性回放。

每一步验证行动者、计时器、视角、事件序号、结果和分数。

### 模型裁判测试

普通测试使用可编程替身，不调用真实供应商。覆盖精确匹配成功、主模型正确或错误、主模型超时后备用模型成功、双模型失败、迟到结果、崩溃恢复和暂存终局覆盖。

真实模型只用于受控集成测试和人工验收。

### UI 验收

验证 2 至 10 人座位布局、当前行动者、触控目标、键盘、屏幕阅读器、非颜色状态提示、私有 DOM 泄漏、断线恢复、等待裁判、异常终止、小局与整场结算、移动端横竖屏和减少动态效果。

## 上架准入

游戏只有同时满足以下条件才能标记为 `playable`：

- 官方规则来源或已确认平台规则完整。
- 权利和授权满足发布要求。
- 规则条款映射完整。
- 单元、契约和完整局测试通过。
- 视角泄漏测试通过。
- 不可变性和确定性测试通过。
- 断线、崩溃恢复和快照迁移通过。
- 机器人完整局可收束。
- 桌面 UI、触控和无障碍验收通过。
- 不包含禁入名称、角色、资产或规则。
- 类型检查、代码检查、全量测试和构建通过。

## 验收指标

### 引擎正确性

- 原语单元测试全部通过。
- 原语输入不可变。
- 相同随机种子与动作序列结果一致。
- 被拒绝动作不产生事件。
- 相同请求不重复副作用。
- 恢复后的状态、视角和计时器与崩溃前一致。
- 外部任务结果可重放且不重复调用模型。

### 迁移游戏

UNO 与《谁是卧底》均通过规则、视角、快照、恢复、机器人、幂等和完整局黄金回放。

### 扩展性

- 新游戏不修改服务端执行平台。
- 不修改稳定原语的业务语义。
- 不增加具体游戏 ID 分支。
- 通用房间、恢复、广播和计时代码零复制。
- 流程、投票和牌区等已有通用逻辑不在新模块重复实现。
- 新游戏模块代码量减少至少 40%。
- 模板到纯规则完整局具有标准路径。

### UI

- 所有游戏共用同一桌面骨架。
- 视觉标记、间距、字体和反馈一致。
- 2 至 10 人布局可用。
- 触控、键盘、屏幕阅读器和减少动态效果达标。
- 私有信息不存在 DOM 泄漏。
- 等待、恢复、暂停和异常状态表现统一。

### 产品与合规

- 获授权游戏按可靠官方规则 1:1 复刻。
- 每条规则具备来源、实现和测试映射。
- 资料不完整的游戏不得上架。
- 《骗子酒馆》永久不进入最终产品。
- 媒体能力不阻塞纯状态引擎。
- WebRTC 定向传输和权限控制通过独立安全评审。

## 规范性词汇

- `MUST`：本阶段必须实现并验收。
- `MUST NOT`：明确禁止。
- `SHOULD`：默认实现，延期必须登记例外。
- `MAY`：非阻塞增强。
- `EXAMPLE`：非穷举示例，不形成封闭契约。
- `DEFERRED`：不属于本阶段，不得创建生产接口占位。

文中“必须”“不得”对应 `MUST` 与 `MUST NOT`。能力名称列表属于 `EXAMPLE`；编码前必须将实际能力定义为版本化封闭枚举，未知能力按契约错误处理。

## 非目标

- 本阶段不建设声明式规则 DSL。
- 本阶段不建设可视化规则编辑器。
- WebRTC、音视频权限和定向传输全部标记为 `DEFERRED`；本阶段不得预建生产接口、数据表或运行时占位。
- 本阶段不为未授权游戏补写或猜测官方规则。
- 本阶段不对所有候选游戏同时迁移。
- 本阶段不以减少代码量为理由合并语义不同的规则。
