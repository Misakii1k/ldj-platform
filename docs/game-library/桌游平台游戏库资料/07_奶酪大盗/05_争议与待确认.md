# 05 争议与待确认

## 1 上线阻塞项

| 事项 | 当前判断 | 需要的证据或决定 |
|---|---|---|
| 正式支持人数 | 常见资料为 4–8 人，但版本可能不同 | 目标发行版盒背与规则书 |
| 单局指认流程 | 二手说明存在投票/同时指人等差异 | 逐字核对正式规则书 |
| 平票处理 | 未可靠确认 | 规则书对应段落 |
| 是否允许弃权或改票 | 未可靠确认 | 规则书对应段落 |
| 奶酪未被盗时如何结算 | 可能在多人同点时出现 | 官方 FAQ 或规则书 |
| 低人数特殊规则 | 部分传播版本可能有幽灵或额外处理 | 对应人数章节 |
| 小偷是否必须主动拿取 | 实体动作与数字自动化可能不同 | 原版夜晚流程原文 |
| 天亮公开哪些桌面信息 | 影响讨论信息量 | 官方示例与流程图 |

这些项目未确认前，可以做原型和数据模型，但不能宣称完成“官方规则模式”。

## 2 容易误写为官方的内容

- 固定 120 秒讨论。
- 所有人秘密投票且简单多数决。
- 小偷在平票时自动获胜。
- 玩家可以随时回看自己的骰点。
- 系统自动替唯一醒来者拿走奶酪。
- 完整时间轴赛后对所有人公开。

以上均可成为合理的数字化方案，但在拿到规则依据前只能标为**建议**。

## 3 机制解释争议

“同一时刻多人醒来就不能偷”的直观解释是彼此目击，符合游戏核心推理结构。但仍应确认规则是否允许某些人数、特殊组件或版本打破这一判断。

“小偷本人是否立即知道身份”在实体桌上通常由其亲手拿走奶酪自然得知；若数字版自动处理，界面必须明确告知该玩家，否则会改变其白天发言策略。

## 4 产品决策

1. 选择一个发行版作为“标准规则”，记录语言、年份和规则书版本。
2. 将任何平台改动集中展示在开房设置中，不在规则正文里悄然替换。
3. 决定夜间是否全程等长。建议等长，减少侧信道。
4. 决定本人是否可回看骰点。建议允许，降低线上记忆负担，同时标记为辅助功能。
5. 决定赛后是否公开完整目击图。建议标准休闲房公开，竞技房在整场结束后公开。
6. 决定断线玩家的投票与超时行为，避免房主临时裁定。

## 5 版权与命名

游戏名称、规则表达、包装、美术、角色造型及组件图的权利边界需法务确认。机制可以被重新表达，但不代表可直接复制规则书文字或官方插画。若平台没有授权，应使用原创文案与美术，并审慎评估是否能使用中文译名和英文商品名。

## 6 验收前核对

规则负责人应把正式规则书逐段映射到准备、掷骰、1–6 点、盗取、讨论、指认、平票和结算。产品负责人确认所有非原版内容都带“变体”或“建议”标签；测试人员覆盖无人醒来、多人同点、早期盗取、末时刻盗取、整夜未盗及断线重连。
