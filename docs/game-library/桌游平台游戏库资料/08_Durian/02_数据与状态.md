# 02 数据与状态

## 1 核心实体

| 实体 | 关键字段 | 可见范围 |
|---|---|---|
| 玩家 | 编号、座位、怒气/处罚位置、连接状态 | 公开 |
| 库存卡 | 卡牌编号、各水果数量、持有者、轮次 | 正面除持有者外可见 |
| 未知库存卡 | 卡牌编号、各水果数量 | 检查前对所有玩家隐藏 |
| 订单卡 | 两个可选水果、各自增加量、状态 | 抽出后公开 |
| 订单板 | 各水果累计订单 | 公开 |
| 猩猩卡 | 类型、效果、触发状态 | 按正式规则决定 |
| 店长怒气 | 当前惩罚值、上限 | 公开 |
| 回合 | 当前玩家、上一行动玩家、方向、计时 | 公开 |
| 质疑 | 按铃者、被质疑者、快照、结果 | 结算时公开 |

## 2 信息模型

Durian 的关键不是普通“手牌保密”，而是反向可见：一张库存卡对持有者隐藏，对其他玩家公开。服务端应为每名观察者生成视图，不能简单设置卡牌为公开或私有。

观察者查看自己的座位时只见卡背、卡架和“你不能查看自己的库存”；查看其他座位时见完整水果构成。未知库存卡对所有在局玩家显示卡背，直到按铃检查进入公开阶段。

## 3 阶段状态机

推荐流程：`房间准备 → 轮次布置 → 回合开始 → 按铃窗口 → 抽订单 → 二选一 → 更新订单 → 下一玩家 → 按铃检查 → 判定责任 → 应用处罚 → 提升怒气 → 检查结束条件 → 新一轮或整局结算`。

猩猩卡可能插入抽牌、选择、库存计算或检查阶段，具体插入点待规则确认。

## 4 计算模型

每种水果分别保存 `inventoryTotal` 和 `orderTotal`。检查时，对所有有效库存卡求和，并应用已生效的猩猩卡修正。只要存在一种水果满足 `orderTotal > inventoryTotal`，质疑成立。

系统还应保留按铃瞬间快照，避免结算动画期间卡牌重排导致争议。快照包含库存卡、未知卡、订单板、当前怒气、按铃者、上一行动者和活动效果。

## 5 处罚与怒气

将“店长当前怒气值”和“玩家累计处罚位置”分开建模。一次失败检查产生一条处罚事件，数值来自按铃瞬间的店长怒气。随后怒气变化顺序必须依规则书处理，不能先升级再处罚。

个人达到结束阈值后的状态可为 `仍在局 / 触发结束 / 已淘汰`，最终选哪一种取决于官方规则确认。

## 6 重连

- 重连玩家不能通过加载瞬间看到自己的库存正面。
- 进入检查动画后重连，只恢复当前已公开到的步骤；服务端结算结果不变。
- 订单选择中断线时保留已抽出的二选一牌；超时后随机选、默认左项或本局无操作需要房规决定。
- 多设备同时登录时，所有设备都必须采用同一观察者权限，不能让副设备读取原始卡牌对象。

## 7 历史与复盘

局中历史可公开每次选择了哪种水果、由谁选择、订单累计值和公开效果；不能回溯展示当前持有者自己的库存。检查结算后，已结束轮次的库存可进入公开历史。整局复盘应包含每轮未知卡、真实库存、按铃时差额和受罚者。

## 8 测试边界

至少覆盖订单恰好等于库存、两种水果同时超卖、只有一种超卖、未知卡改变结论、猩猩效果改变结论、首回合按铃、最后一名玩家按铃、处罚恰好达到阈值、处罚越过阈值及重连后的反向可见性。
