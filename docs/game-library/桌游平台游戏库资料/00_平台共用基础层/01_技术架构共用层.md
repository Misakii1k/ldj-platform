# 01 技术架构共用层

> 本文档基于《八款桌游规则与手机端卡牌化研究》研究报告的"共用手机端平台"章节整理，定义平台所有游戏共用的技术架构层。

---

## 1. 统一领域层设计

平台采用统一的领域层流水线，所有游戏模式均遵循以下核心流程：

```
大厅/匹配 → 规则集锁定 → 私密分发 → 回合状态机 → 指令校验 → 公开/私密事件 → 结算账本 → 完整揭示与回放
```

### 1.1 大厅/匹配

- 玩家浏览可用游戏模式，通过房间列表或快速匹配进入对局。
- 大厅服务维护房间状态（等待中、已满员、游戏中、已结束）。
- 匹配算法根据规则集、人数、玩家段位等参数进行组合。
- 房主可配置规则集变体、人数上限、超时阈值等参数。

### 1.2 规则集锁定

- 对局启动时锁定所选规则集（`rulesetId` + 版本号）。
- 规则集定义卡牌清单、角色能力、胜负条件、回合结构等全部游戏参数。
- 锁定后不可变更，确保整局游戏语义一致。
- 支持同一游戏多个规则集并存（如情书经典版 vs 现代版）。

### 1.3 私密分发

- 服务器在游戏开始时向各客户端分发私密信息（手牌、身份、角色、关键词等）。
- 分发原则：**最小知悉原则**——只下发该玩家当前回合有权知道的信息。
- 私密信息在服务端持久化，客户端仅持有临时副本，断线重连时重新下发。

### 1.4 回合状态机

- 每款游戏定义显式的状态机（如情书：`ROUND_SETUP → DEAL → TURN_DRAW → CHOOSE_DISCARD → CHOOSE_TARGET → RESOLVE → ELIMINATION_CHECK → DECK_CHECK → NEXT_TURN`）。
- 状态机由服务器驱动，客户端仅提交动作意图。
- 状态转换包含前置条件校验和原子性保证。
- 回合超时由服务器计时器触发，自动执行默认行为（弃牌、Pass、随机决策等）。

### 1.5 指令校验

- 所有客户端提交的指令必须经过服务器校验：
  - 合法性校验（当前状态是否允许该动作）。
  - 目标校验（目标玩家/卡牌是否合法）。
  - 权限校验（该玩家是否有权执行该动作）。
  - 幂等校验（防止重复提交导致状态异常）。
- 校验失败返回明确错误码，客户端据此展示反馈。

### 1.6 公开/私密事件

- 服务器将每个动作的结果封装为事件，按可见性分级分发（详见《03_事件与可见性规范.md》）。
- 公开事件：所有玩家可见（如弃牌、翻牌、得分）。
- 私密事件：仅特定玩家可见（如私人手牌查看、私密比较结果）。
- 定向事件：指定角色/阵营可见（如同醒者名单、表演双方视频流）。
- 事件包含时间戳、序列号、事件类型和载荷，用于回放和日志审计。

### 1.7 结算账本

- 每局游戏的每轮操作记录在不可篡改的账本中（服务端日志）。
- 账本记录内容：事件序列、时间戳、玩家动作、随机数种子、规则集快照。
- 结算账本用于：
  - 胜负判定追溯。
  - 争议仲裁（举报核查）。
  - 回放系统数据源。
  - 游戏数据分析。

### 1.8 完整揭示与回放

- 游戏结束后，所有隐藏信息逐步揭示（手牌、身份、关键决策点）。
- 揭示顺序由规则集定义，确保信息揭示不破坏游戏完整性。
- 回放系统基于事件日志重建对局，支持快进、倒退、逐帧查看。
- 回放过滤器按玩家视角过滤信息，只显示该玩家当时可见的内容。

## 2. 权威服务器原则

**核心原则：所有随机性、判定和胜负逻辑全部在服务器执行，客户端只提交意图。**

### 2.1 服务器权威的操作清单

| 操作 | 执行方 | 客户端角色 |
|------|--------|-----------|
| 洗牌 | 服务器 | 提交"开始洗牌"意图，等待发牌结果 |
| 骰子 | 服务器 | 提交"掷骰"意图，接收骰面结果 |
| 角色分配 | 服务器 | 接收角色下发 |
| 目标选择 | 服务器 | 提交目标选择，服务器校验合法性 |
| 抢答排序 | 服务器 | 提交抢答时间戳，服务器排序 |
| 胜负判定 | 服务器 | 接收胜负结果展示 |
| 身份揭示 | 服务器 | 接收揭示事件 |

### 2.2 安全约束

- 客户端不参与任何随机数生成，随机种子由服务器主线程生成并记录。
- 客户端不提前接收未授权的信息（如尚未翻开的牌、尚未揭示的身份）。
- 服务端对所有客户端指令进行时间戳校验，防止重放攻击。
- 关键操作（洗牌、掷骰、发牌）使用幂等指令，防止网络重试导致重复执行。

### 2.3 抗作弊机制

- 服务端记录所有操作的时间戳和序列号，客户端无法伪造。
- 敏感操作（如手牌查看）在服务端日志中记录查看者和被查看者。
- 对局结束后可导出完整事件日志进行审计。
- 客户端代码应做混淆处理，防止逆向工程修改UI显示逻辑。

## 3. 分级可见性机制

每个事件在生成时声明其接收范围，服务器按范围进行分发。

### 3.1 可见性级别

| 级别 | 名称 | 描述 | 示例 |
|------|------|------|------|
| L0 | 全局公开 | 所有玩家可见 | 弃牌、翻牌、得分、淘汰 |
| L1 | 本人私密 | 仅动作执行者可见 | 自己抽到的牌、私密查看结果 |
| L2 | 双方私密 | 动作执行者和目标可见 | 牧师查看手牌、男爵比较 |
| L3 | 同队可见 | 同一阵营/角色组可见 | 同醒者名单、恶鹅同伙 |
| L4 | 定向传递 | 指定接收者可见 | 以鹅传鹅的视频流、表演者沟通 |
| L5 | 结算揭示 | 对局结束后公开 | 最终身份揭示、隐藏信息展示 |

### 3.2 分发策略

- 服务器在事件分发前根据可见性级别过滤接收者列表。
- 客户端不接收任何超出其可见性范围的事件数据。
- 事件载荷中不包含任何接收者不应知晓的信息（即使字段值为空也不下发）。
- 防止侧信道攻击：对于不同玩家接收不同内容的事件，保持事件包大小和时序一致。

### 3.3 侧信道防护

- 对于需要等长响应时间的操作（如夜间阶段、抢答窗口），服务器发送等长的节拍包，所有客户端在同一时间收到响应。
- 私密视图操作（如查看手牌）的加载时间标准化，防止通过响应时间推断信息。
- 声音和动画反馈与内容解耦，不包含信息泄露。

## 4. 版本化规则

### 4.1 规则版本管理

- 每局游戏持久化记录 `rulesetId`、版本号（`semver` 格式）和完整配置快照。
- 规则集定义包含：
  - 元数据：名称、版本、作者、来源、版权信息。
  - 卡牌定义：每张牌的 ID、名称、数值、数量、效果、目标条件。
  - 状态机定义：状态列表、转换条件、阶段配置。
  - 参数配置：人数范围、超时阈值、胜负门槛、特殊规则变体。
- 规则集存储在服务端，客户端按需加载，不硬编码在客户端二进制中。

### 4.2 配置快照

- 对局开始时刻，将规则集的完整配置（包括所有参数）序列化为 JSON 快照。
- 快照随对局日志持久化存储，用于复盘和争议仲裁。
- 快照包含对局自定义的房规参数（如超时时间、平票规则、特殊变体）。

### 4.3 向后兼容

- 更新规则集后，旧对局仍可使用原始快照进行回放。
- 规则集 ID 不变但版本号升级时，新对局使用新版本，旧对局不受影响。
- 支持规则集的多版本并行运行（如情书经典版 v1.0 和 v1.1 可同时存在）。

## 5. 断线恢复机制

### 5.1 快照策略

- 服务器在每个关键节点（状态转换后）生成对局快照。
- 快照按玩家过滤：只包含该玩家有权知道的信息（遵循可见性分级）。
- 快照包含：当前状态、手牌（仅该玩家的）、可见公开信息、事件序列号。
- 快照保存在服务端内存和持久化存储中。

### 5.2 重连流程

```
检测断线 → 客户端请求重连 → 身份验证 → 获取过滤快照 → 重建客户端状态 → 同步到最新事件
```

1. 客户端检测到断线后自动尝试重连（指数退避策略）。
2. 重连请求携带对局 ID 和玩家令牌。
3. 服务器验证身份，返回该玩家的过滤快照。
4. 客户端根据快照重建本地状态（UI、手牌、可见信息）。
5. 服务器推送断线期间错过的所有事件（按序列号增量同步）。
6. 客户端同步到最新状态，恢复游戏交互。

### 5.3 幂等指令

- 敏感动作（弃牌、掷骰、发牌）使用幂等指令 ID。
- 客户端重试时携带相同的指令 ID，服务器检测到已执行则返回已有结果，不重复执行。
- 递增版本号机制：每个客户端维护一个动作版本号，服务器拒绝已应用的旧版本指令。

### 5.4 托管机制

- 玩家断线超时后进入托管状态。
- 托管行为由规则集定义（如随机弃牌、Pass、自动跟注等）。
- 托管期间服务器模拟玩家决策，确保对局继续。
- 玩家重连后立即退出托管，恢复手动操作。
- 托管行为记录在事件日志中，标记为"托管"。

### 5.5 房主迁移

- 房主断线超时后，自动将房主权限迁移给对局中最早加入的玩家。
- 迁移过程服务端原子操作，无需玩家投票确认。
- 新房主获得房间管理权限（踢人、修改房规、解散房间等）。

## 6. 建议产品路线

基于研究报告对八款游戏的分析，建议按以下阶段推进开发：

| 阶段 | 内容 | 核心能力 | 验收标准 |
|------|------|---------|---------|
| **MVP 1** | 情书（现代版 + 经典版） | 规则闭合、无需语音、可验证边界多 | 20 个确定性规则用例全部通过 |
| **MVP 2** | Durian | 复用卡牌、房间、抢答与私密视图引擎 | 取得完整规则书和逐张牌表 |
| **MVP 3** | 伪人测试 | 加入语音、举报、内容治理系统 | 12 人语音弱网与隐私测试通过 |
| **MVP 4** | 奶酪大盗 / 以鹅传鹅 | 复杂私密频道、视频或主持流程 | 侧信道防护、重连和媒体授权测试通过 |
| **暂缓** | Ding、囚徒之夜 | 官方规则和版本信息不足 | 待正版规则书、组件与授权补齐 |

### 6.1 架构复用策略

- **MVP 1（情书）**：搭建基础架构——房间管理、规则集引擎、回合状态机、事件系统、断线重连。
- **MVP 2（Durian）**：验证私密视图引擎、抢答/按铃机制、反向信息分发。
- **MVP 3（伪人测试）**：集成语音频道、举报系统、内容审核、敏感词过滤。
- **MVP 4（奶酪大盗/以鹅传鹅）**：扩展私密频道为媒体通道（视频/音频），引入主持流程。

## 7. 非功能需求

### 7.1 性能要求

- 回合制游戏：操作延迟 < 200ms（服务端响应）。
- 实时抢答：端到端延迟 < 100ms（含网络传输）。
- 语音频道：端到端延迟 < 150ms（WebRTC）。
- 对局快照恢复：< 1s（从请求到客户端重建完成）。

### 7.2 可用性

- 服务器可用性 > 99.9%（SLA）。
- 断线重连成功率 > 99%（弱网环境下）。
- 支持跨区域部署，玩家就近接入。

### 7.3 安全

- 所有对局通信使用 TLS 加密。
- 敏感操作日志保留至少 90 天。
- 客户端反作弊检测：异常频率操作的自动限流和告警。
