# 03 事件与可见性规范

> 本文档基于《八款桌游规则与手机端卡牌化研究》研究报告的"共用手机端平台"章节中"分级可见性"部分扩展，定义平台事件系统的分类、可见性策略、日志格式和回放设计。

---

## 1. 事件类型

平台事件系统将每个游戏动作的结果封装为结构化事件，按可见性范围分为三类。

### 1.1 公共事件

**定义**：所有玩家都可以接收和查看的事件。

**特征**：
- 接收者列表 = 对局中所有玩家。
- 事件载荷包含完整信息，无信息隐藏。
- 事件日志对所有玩家开放。

**典型场景**：
| 游戏 | 公共事件示例 |
|------|-------------|
| 情书 | 玩家 X 弃牌（显示牌面）、玩家 X 被淘汰 |
| Durian | 玩家 X 按铃、订单板更新、店长愤怒升级 |
| 伪人测试 | 问题公开、投票结果、计分更新 |
| 奶酪大盗 | 黎明到来、投票开始、身份揭示 |
| 以鹅传鹅 | 逐棒传递完成、指认开始、阵营结算 |

**实现要求**：
- 公共事件在事件总线上广播给所有已连接客户端。
- 断线重连时，服务器推送所有错过的公共事件。
- 公共事件按序列号严格排序，客户端按序消费。

### 1.2 私密事件

**定义**：仅特定玩家可以接收的事件，其他玩家既不知道事件内容，也不知道事件发生。

**特征**：
- 接收者列表 = 单个玩家或限定玩家集合。
- 未授权的玩家不收到该事件，也不知晓该事件已发生。
- 事件载荷包含仅接收者有权知道的信息。

**典型场景**：
| 游戏 | 私密事件示例 | 接收者 |
|------|-------------|--------|
| 情书 | 牧师查看玩家 X 手牌 | 牧师本人 |
| 情书 | 男爵比较结果（数值高低） | 比较双方 |
| 情书 | 国王交换手牌 | 交换双方 |
| Durian | 下发自己的库存牌（不显示） | 除自己外的所有玩家 |
| Durian | 抽到的订单牌 | 当前回合玩家 |
| 伪人测试 | 下发身份（人类/伪人） | 每人仅见自己身份 |
| 伪人测试 | 关键词下发 | 伪人接收关键词 |
| 奶酪大盗 | 夜间独醒名单 | 独醒玩家 |
| 奶酪大盗 | 大盗偷奶酪结果 | 大盗本人 |

**实现要求**：
- 私密事件使用点对点推送，不经过事件广播。
- 服务端在事件分发时按接收者列表精确传递。
- 事件日志中私密事件仅对接收者可见。
- 防止侧信道：私密事件的发送时机和包大小不泄露信息。

### 1.3 定向事件

**定义**：事件内容公开，但仅特定接收者可以在事件发生时立即查看，其他玩家在事件发生后或特定条件下才能查看。

**特征**：
- 接收者列表 = 指定角色、阵营或玩家组。
- 事件内容在事件日志中记录，但对非接收者默认隐藏，直到满足揭示条件。
- 定向事件是私密事件和公共事件的中间形态。

**典型场景**：
| 游戏 | 定向事件示例 | 接收者 | 公开条件 |
|------|-------------|--------|---------|
| 以鹅传鹅 | 表演视频流 | 表演者和接收者 | 对局结束后全员可见 |
| 奶酪大盗 | 同醒者名单 | 同醒的玩家 | 黎明后部分公开 |
| 伪人测试 | 判官模式下的回答 | 判官本人 | 指认阶段后公开 |
| 囚徒之夜 | Yes/No 回答矩阵 | 所有玩家见自己回答，矩阵仅公开计数 | 终局揭示后全公开 |

**实现要求**：
- 定向事件在事件总线上打标签，客户端根据权限过滤。
- 事件日志中定向事件记录完整载荷，但访问权限受控。
- 揭示条件满足后，定向事件自动转为公共事件或向指定范围公开。

## 2. 可见性分级策略

### 2.1 可见性级别定义

平台采用六级可见性分级体系：

| 级别 | 代码 | 名称 | 分发范围 | 示例 |
|------|------|------|---------|------|
| L0 | `PUBLIC` | 全局公开 | 所有玩家（含观战） | 弃牌、得分、淘汰 |
| L1 | `PRIVATE_SELF` | 本人私密 | 仅动作执行者 | 手牌下发、私密查看 |
| L2 | `PRIVATE_BOTH` | 双方私密 | 执行者 + 目标 | 牧师查看、男爵比较 |
| L3 | `GROUP` | 同组可见 | 同阵营/同角色组 | 同醒者、恶鹅同伙 |
| L4 | `DIRECTED` | 定向传递 | 指定接收者列表 | 视频流、私密频道 |
| L5 | `REVEAL` | 结算揭示 | 对局结束后全员 | 身份揭示、隐藏信息 |

### 2.2 可见性策略配置

每个事件在规则集定义中声明其可见性级别：

```json
{
  "eventType": "CARD_DISCARD",
  "visibility": "PUBLIC",
  "payload": {
    "playerId": "player_01",
    "cardId": "love_letter_guard_01",
    "cardValue": 1
  }
}
```

```json
{
  "eventType": "PRIEST_VIEW",
  "visibility": "PRIVATE_BOTH",
  "receivers": ["player_01", "player_03"],
  "payload": {
    "viewerId": "player_01",
    "targetId": "player_03",
    "viewedCard": {
      "cardId": "love_letter_princess_01",
      "cardValue": 8
    }
  }
}
```

### 2.3 可见性继承规则

- 子事件继承父事件的可见性级别。
- 特殊情况下，子事件可提升可见性（如私密查看结果在结算时转为公开）。
- 可见性转换必须在规则集中显式声明。

### 2.4 侧信道防护策略

| 防护目标 | 实现方式 |
|---------|---------|
| 防止通过事件接收时机推断信息 | 所有玩家在相同时间窗口接收事件，私密事件使用等长节拍包 |
| 防止通过事件包大小推断信息 | 固定长度的事件帧，不足部分填充随机数据 |
| 防止通过响应时间推断信息 | 服务端响应时间标准化，私密操作加入随机延迟 |
| 防止通过 UI 反馈推断信息 | 声音/动画反馈与内容解耦，不包含信息泄露 |

## 3. 事件日志格式

### 3.1 事件结构

```
{
  "eventId": "evt_20260801_abc12345",
  "gameId": "game_20260801_001",
  "roundId": 3,
  "turnId": 5,
  "sequenceNumber": 142,
  "timestamp": "2026-08-01T14:30:22.123Z",
  "eventType": "CARD_DISCARD",
  "visibility": "PUBLIC",
  "actorId": "player_01",
  "targetIds": [],
  "payload": { ... },
  "signature": "sha256 hash for integrity"
}
```

### 3.2 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `eventId` | string | 全局唯一事件 ID，格式：`evt_{日期}_{随机数}` |
| `gameId` | string | 对局 ID |
| `roundId` | int | 轮次编号 |
| `turnId` | int | 回合编号 |
| `sequenceNumber` | int64 | 全局递增序列号，用于事件排序和断线同步 |
| `timestamp` | ISO8601 | 事件生成时间（服务端时间） |
| `eventType` | string | 事件类型，命名格式：`{MODULE}_{ACTION}` |
| `visibility` | enum | 可见性级别：`PUBLIC` / `PRIVATE_SELF` / `PRIVATE_BOTH` / `GROUP` / `DIRECTED` / `REVEAL` |
| `actorId` | string | 动作执行者 ID |
| `targetIds` | string[] | 目标玩家 ID 列表 |
| `payload` | object | 事件载荷，包含事件具体数据 |
| `signature` | string | 事件签名，用于完整性校验 |

### 3.3 事件类型命名规范

- 格式：`{领域}_{动作}`（如 `CARD_DISCARD`、`PLAYER_ELIMINATE`、`VOTE_SUBMIT`）。
- 领域前缀：`CARD`（卡牌）、`PLAYER`（玩家）、`ROUND`（轮次）、`VOTE`（投票）、`GAME`（对局）、`CHAT`（聊天）、`SYSTEM`（系统）。
- 动作后缀：`DISCARD`（弃置）、`DRAW`（摸牌）、`PLAY`（打出）、`RESOLVE`（结算）、`ELIMINATE`（淘汰）、`REVEAL`（揭示）、`SCORE`（计分）。

### 3.4 日志存储

- 事件日志持久化存储，保留至少 90 天。
- 日志按 `gameId` 分片，每片包含该对局的完整事件序列。
- 日志支持按 `eventType`、`playerId`、`timestamp` 检索。
- 日志导出格式：JSON Lines（`.jsonl`）或压缩归档（`.jsonl.gz`）。
- 私密事件在日志中标记接收者，非接收者查询时返回脱敏数据。

### 3.5 日志完整性

- 事件日志使用哈希链保证完整性：每个事件包含前一个事件的哈希值。
- 日志可导出为不可篡改的审计报告。
- 对局结束后，可生成事件日志的校验和用于争议仲裁。

## 4. 回放系统设计要点

### 4.1 回放数据源

- 回放系统以事件日志为唯一数据源，不依赖客户端状态。
- 回放文件包含：对局元数据 + 完整事件序列 + 规则集快照。
- 回放文件格式：JSON 或协议缓冲区（Protocol Buffers）序列化。

### 4.2 回放核心功能

| 功能 | 说明 |
|------|------|
| 播放/暂停 | 标准视频播放控制 |
| 速度控制 | 0.5x / 1x / 2x / 4x 倍速播放 |
| 逐帧前进/后退 | 按事件序列逐步推进或回退 |
| 跳转到指定事件 | 按事件序列号或轮次/回合跳转 |
| 单步模式 | 每按一次前进一个事件，适合教学分析 |

### 4.3 视角过滤

- **全知视角**：所有事件可见，适合裁判/教学/复盘。
- **玩家视角**：仅显示该玩家在当时可见的信息（遵循可见性分级）。
- **观战视角**：延迟 30 秒显示，隐藏私密信息。
- **关键事件视角**：仅显示关键决策点（如弃牌、投票、揭示）。

### 4.4 回放UI要素

- 时间轴：显示事件序列，标记关键事件。
- 玩家信息面板：展示每个玩家的状态变化。
- 操作记录：显示每个玩家的操作历史和手牌历史。
- 信息揭示动画：在结算揭示时，自动展示隐藏信息。

### 4.5 回放生成与分享

- 对局结束后自动生成回放链接。
- 回放链接有效期：默认 30 天。
- 回放可设置访问权限（公开/仅好友/仅参与者）。
- 回放可导出为独立文件分享。

### 4.6 回放安全

- 回放数据不包含敏感信息（如玩家真实姓名、IP 地址）。
- 回放文件签名验证，防止篡改。
- 回放中涉及被封禁玩家的内容，自动脱敏处理。
