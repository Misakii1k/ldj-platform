## 推荐处理方式

1. **G0：确认产品默认值及视觉方向**。本包不是“所有设计均已获用户批准”。
2. 先实现无 UI 的规则与黄金测试，再接既有状态机和持久化，跑通一局。
3. 用固定视角样例实现前端，确认 3 个关键画面，再铺齐所有状态。
4. 单独接 WebSocket 与交互，跑多客户端、刷新、超时、崩溃恢复。
5. 全量验收、构建客户端产物；Android 内嵌主机若要交付还要重建服务器载荷。

**不要**同时叫一个小模型做“全部逻辑 + 全部 UI + 全部题库”。每个任务一个可验证输出。
**不要**要求每个执行者通读整个仓库。先读 STATUS、规则以及当前任务引用的材料。
**不要**通过自动重试、删断言、改截图基准来假装通过。

## 关键选择与成本

- 推荐：2D 轻桌面表现 + 现有 React/WS/SQLite/GameModuleV2，零新增运行服务。
- 不选：单页伪联机原型作为产品交付（快，但无法保证秘密、恢复、结算）。
- 不选：3D 桌台、物理筹码、多规则版本、多设备队伍权限同时开工（返工面过大）。
- 首版无真实 LLM 调用；玩法本身不需要 AI。规则陪练后置，不能让付费机器人调用成为测试依赖。
- 真正的开发成本重点是题库审校、投注账本、保密和重连，不是“摆几个数字卡片”。

## 防偏离优先级

当前用户明确决策 > G0 已确认并版本化的本包 > 黄金预期/协议 > 执行任务卡 > 示例旧游戏代码。
若规则文字与黄金预期矛盾，**停止该部分并报告矛盾**，不能自行挑一份改另一份。
原始研究报告仅作历史背景；已发现错误，不再作为实现依据。官网规则书提供可核查的参照，但不能偷偷覆盖用户选择的平局规则。

## 范围与批准

用户已选择：按照最后发来的规则尝试，允许询问不确定项。
本包建议：3–7 个席位、七轮；同队共用一部设备；每席位一个提交身份；自动计分、免费筹码2枚；无充值提现。
尚未批准：超时补答/未下注处理、次级平局处理、数值上限、首发题库规模、具体视觉风格、队伍设备范围。见 01 的 G0。
在 G0 前，仅可做源码勘察、纯规则算例和不产生产品行为的测试设计；不要擅自将游戏设成 playable。
