# 聚乐桌游 · 设计基调（Design Direction）

> **任何画面相关任务开工前先读本文件。** 它回答"要做成什么样"；`docs/design-spec.md` 回答"用什么令牌和组件做"；`AGENTS.md`「视觉验收规范」回答"怎么算做完"。
> 三者冲突时以本文件的「已确认」条目为准。本文件只有用户能改「已确认」，AI 只能往「待验证推测」里加东西。

最后更新：2026-09-26。

---

## 1. 一句话基调

**每款游戏是一个独立的小世界，共用同一套手感；画面主体突出、适度留白；关键时刻要有 Balatro 式的打击感。**

## 3. 两种表皮

C1 + C2 落地成两种表皮。每款游戏属于哪种以 C12 为准；C12 里没列的游戏，打磨前先问用户。

| | 浅色派对表皮 | 深色悬疑表皮 |
|---|---|---|
| 底 | 该游戏自己的场景色（果摊、牧场、派对桌），不是通用奶油纸铺满 | 深色场景（夜、木刻、剧场），径向舞台光 |
| 物件（牌、席位牌、按钮、弹窗） | 3px 墨黑粗边 + 硬切下沉投影（`--gp-shadow*`） | 1–1.5px 暗色或金色细边 + 贴纸阴影（`--gp-shadow-sticker`） |
| 黄色 | 只给唯一主 CTA，不做大面积底色 | 同左；可用金色 accent 做描边与大字 |
| **已确认** | 榴莲、奶酪大盗、情书、斗地主、UNO、Ding、伪人测试、囚徒之夜（谁是狱警） | 狼人杀、谁是卧底、一智千金 |
| 未定（先问） | 以鹅传鹅、大富翁、平台大厅/房间页 | |

## 4. 构图规则（C3 的具体化）

1. 中央主舞台占视口面积约 50%–60%，一眼能看出"现在在干什么"：当前阶段、当前焦点物件、倒计时。
2. 席位环绕主舞台（左右或环形），不压在舞台上；手机竖屏席位可收到上下两条，但不需要滚动才能看全。
3. 留白由三样东西撑住：`--gp-stage-light` 舞台光、`.stage-art` 专属剪影（12% 透明）、`--gp-font-display` 大字。**不用小装饰、小标签、小面板去填空白。**
4. 每个视口只有一个黄色主按钮，贴底部操作区。
5. 反例（出现即不合格）：一张 `.gp-panel` 居中、四周空白；舞台中央只有一行文字；席位和信息面板挤满全屏没有焦点。

## 5. 打击感（C5 的具体化，以 Balatro 为参照）

Balatro 只取"打击感与计分演出"和"牌的手感"（C13），不取配色和像素风。落到本项目：

| 时刻 | 必须有的演出 | 参考实现 |
|---|---|---|
| 悬停/选中物件 | 牌轻微倾斜 + 上浮，释放后回弹 | `CardFanEngine` 相邻联动 |
| 出牌 / 传递 / 下注 | 物件从出发点**飞**到目标点，不瞬移 | `.stage-flight-layer` / `FlightLayer` |
| 得分 / 数字变化 | 数字逐位滚动，变化瞬间放大弹一下；大额得分逐项累加计数 | `RollingNumber` |
| 揭晓（身份、答案、翻牌） | 翻转 + 短暂停顿 + accent 扫光；配音效 | `IdentityFlipCard` |
| 结算 / 胜负 | 分数逐行入场并计数，胜者有明显高光；可轻微屏震（≤4px） | `TabletopSettlementDock` |
| 倒计时最后 10 秒 | 进度环变色，最后 5 秒滴答 + 脉冲 | `.stage-countdown` |

**边界**：演出只动 `transform` / `opacity`；单次演出 ≤ 600ms（结算逐行累计除外）；四档 `data-motion-level` 降级照 `design-spec.md` §3.2；`reduced` 档保留关键反馈，停装饰循环。

## 6. HTML 方向稿流程（C6 的具体化）

1. **位置**：`docs/ui-preview/<game>/directions/`，每个方向一个独立 `.html`（内联 CSS，不依赖构建，双击能打开）。
2. **数量**：2–3 个，彼此差异要大到一眼能分清（换构图或换表皮，不是只换颜色）。
3. **内容**：同一个关键画面、同一份固定假数据（真实人数、昵称、牌面、分数）；桌面 1280×800 与手机 390×844 两个视口并排或可切换。
4. **说明**：每个方向稿顶部写三行——方向名、对标（C4 里的哪个）、与其他方向的主要差别。
5. **交付**：把绝对路径发给用户，**不写评价**；用户挑一个或指出哪里不对，定稿后才写视觉契约、动正式代码。
6. 方向稿里被用户否定的东西，追加到本文件 §2（"否定过"），避免下次再犯。
7. **定稿后交接给执行模型**（2026-09-26 用户确定的分工：「我找你来定稿。定完之后，你把详细流程或者计划做一下，之后我交给其他更便宜、更快速的模型去做。」）：
   - 强模型负责：问清需求 → 方向稿 → 用户定稿 → 写**交接计划**。
   - 交接计划放在 `docs/plans/<日期>-<game>-visual/`，必须能让没参与讨论的模型照做不走样：定稿方向稿路径（它就是像素参照）、视觉契约（§11.2 六节）、文件白名单、逐步任务（每步给出要改的文件、要做到的效果、完成判据）、验证命令、截图组清单、"不许做"清单（本文件 §2 的否定项 + 该游戏的特定禁区）。
   - 执行模型只照计划实现，**不做新的视觉决定**；遇到计划没写的，停下列问题交回用户，不自行发挥（C14）。
   - 执行完照 AGENTS.md 视觉验收规范出截图组，由用户看图判定；不合格的原话记回计划。

## 7. 出方向稿前的自检清单

给用户看之前逐条过一遍，有一条不满足就先改：

- [ ] 这款游戏的"世界"是什么，一句话说得出来吗？画面里看得出来吗？
- [ ] 表皮选对了吗（浅色粗边 / 深色细边）？
- [ ] 中央主舞台是否一眼看出"现在在干什么"？
- [ ] 有没有一张 `.gp-panel` 居中、四周空白的反例构图？
- [ ] 留白是用舞台光、剪影、大字撑的，还是用小碎片填的？
- [ ] 大数字是衬线吗？
- [ ] 黄色是否只出现在一个主按钮上？
- [ ] 关键时刻的演出在方向稿里至少示意了一个（可用 CSS 动画或并排的前后两帧）？
- [ ] 是否与狼人杀 / 榴莲放在一起不突兀，像同一个平台？
- [ ] 是否避开了 §2 里所有"否定过"的做法？
